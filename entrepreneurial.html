Problem / Product Goal
Automate a physical cooking process

Develop a self-contained controller that senses plant temperature and automatically positions a physical mechanism rather than depending on repeated manual adjustment.

System Architecture
Sensor → control law → motor drive

Functional architecture partitions temperature sensing, controller logic, motor-position feedback, motor drive, mechanical actuation, and the grill as the controlled plant.

Detailed Engineering
STM32 + embedded C + PI control

Designed electronics and PI control laws for a brushed DC motor using PWM, feedback loops on motor position and plant temperature, plus custom mechanical drive components.

Integration / Evidence
Prototype, instrumentation, measured response

Development progressed through bench electronics, control-law tuning, mechanical integration, oscilloscope/test instrumentation, and integrated operation with measured temperature response.

System Thinking / Design Progression

Continuous Engineering Progression

A deliberately simple consumer problem was carried through one continuous engineering progression: identify the need, trade concepts, define architecture, derive requirements, allocate functions, define control behavior, integrate the hardware and software, and verify measured system performance.

01
Identify Need
Make the grill tend itself

Objective: eliminate continuous manual grill tending by creating a machine that automatically manages cooking temperature.

Starting point: “I wanted a machine to mind the grill for me.”
02
Concept Trade Study
Choose the temperature-control mechanism

Compared direct gas-valve control with moving the grill lid. Valve control promised lower fuel use and potentially faster response, but required a mechanically complex custom-machined assembly. Lid-position control used more propane but could be fabricated from standard metal parts.

Selected concept: lid-position control—simpler physical implementation, with visible motion that also made system behavior easy to observe.
03
Physical Architecture
Define how the product interacts with the grill

Placed the lift actuator on the grill side table. The actuator raises the lid to cool the grill, while a thermocouple measures grill temperature.

Physical concept connects the new mechanism to an otherwise conventional grill with minimal modification.

04
Functional Architecture
Close the temperature-control loop

Structured the system as a feedback loop: temperature input → controller → actuator → grill lid → grill temperature → thermocouple feedback.

The architecture separates sensing, control, actuation, and the physical plant before hardware and software details are chosen.
Original design drawing • click to enlarge
05
Derived Mechanical Requirements
Turn the concept into measurable lift requirements

A survey of typical home grills established a 10–40 lb lid-weight range. The lift point was conservatively treated at 50% of lid depth, coincident with the assumed center of mass.

Lift ≥ 40 lbSlew ≥ 5 in/min
These requirements flow from the selected lid-control architecture and the temperature-control need.
Original lift-point sketch • click to enlarge
06
Actuator Requirements
Flow lift requirements into motor / leadscrew sizing

Linear motion drove selection of a leadscrew and motor combination. The 40 lb lift requirement and 5 in/min slew requirement were then translated into motor torque and speed using leadscrew geometry.

Lift force ← motor torque / leadscrew pitch
Linear rate ← motor rev/min / threads per inch
System-level performance requirements now constrain component-level mechanical and motor choices.
07
Function Allocation
Partition behavior across software, hardware, and physical plant

Allocated temperature control, motor-position command, position conversion, deadband, sensor interfaces, motor actuation, and thermal response across three explicit layers.

Software layerHardware layerPhysical plant
The allocation diagram makes implementation boundaries and feedback paths visible before detailed coding and electronics design.

08
Control-Law Definition
Refine the architecture into dynamic control behavior

Expanded the allocated architecture into a control model with proportional/integral temperature control, motor-position feedback, deadband, Hall-effect position sensing, actuator dynamics, and a simplified thermal-plant model.

This milestone bridges system architecture and the detailed embedded control implementation that followed.

09
Model-Based Design
Select filter coefficients with a modelling tool

Used MicroModeler to define the filter response and select coefficients before implementing the filter in the embedded controller.

The detailed signal-conditioning design continued directly from the control-law definition rather than beginning a separate development phase.

10
Bench Integration
Integrate motor and embedded controller

Integrated the motor, controller electronics, sensors, and drive functions on the bench before committing them to the complete mechanical assembly.

Bench integration provided a controlled environment for verifying the electronics and motion-control behavior before full-system assembly.
Bench integration • click to enlarge
11
Full-System Prototype
Integrate electronics, control, and mechanical actuation

Combined the embedded controller, motor drive, sensing, lid-lift mechanism, and grill interface into a complete working prototype.

This step demonstrated that the earlier architecture, requirements, allocation, and control decisions could operate together as one physical system.
12
System Test & Refinement
Measure closed-loop temperature performance

System testing was used to refine the control laws and verify the integrated response, resulting in a grill-temperature profile controlled to within 20 degrees.

Measured system response closed the development sequence with objective performance evidence from the working prototype.

Product Goal

Racquets are differentiated by their moments of inertia about the grip point, aka "swingweight". Commercial meters to measure this are heavy and expensive. I targeted a compact standalone swingweight around a $100 retail concept, optimized for portability and simple operation.

Measurement Architecture
Gravity-restored pendulum + gyro

Determines oscillation period from rate-gyro zero crossings, then computes swingweight using known fixture mass, pivot geometry, and racket parameters.

Embedded Implementation
High-rate IMU + local UI

Firmware performs stillness qualification, gyro-bias handling, high-rate sampling, zero-crossing detection, period calculation, calibration storage, and local display/user input.

Engineering Focus
Accuracy, latency, repeatability

Design work compared IMU response, sample rate, sensor lag, fixture geometry, mounting alignment, and competing spring-based measurement methods.

User Problem
Completed laundry gets forgotten

The product addresses the common failure mode where the user leaves the laundry area, the cycle finishes, and clothing remains in the washer because the completion cue is no longer noticed.

Product Architecture
Machine sensor + remote receiver

A compact sensor clips or mounts to the washer, while a separate receiver remains in the user's living area to make completion status persistent and visible.

User Simplicity drives Architecture

The design deliberately avoids user needing to setup accounts, do phone pairing, setup anything. The user magnetically attaches one unit on the washer and places the other unit in a living area. The software creates a private wifi network automatically between the two units and simply begins working.

Product Communication
Simple physical story

The concept was developed around an immediately understandable sequence: laundry is forgotten, the receiver visibly reminds the user, and recognition triggers action without another digital workflow.
